# Исследование источников и рендеринга текстов песен для NeDotify Windows

Дата: 2026-10-28. Исходники внешних проектов проверены на зафиксированных коммитах; репозитории клонировались во временную папку вне проекта. Это сравнение архитектур и возможность интеграции, а не утверждение о доступности/лицензионной пригодности конкретных текстов.

## Краткий вывод

1. **Кандидат к отдельной интеграции для NeDotify — Better Lyrics API**: у сервиса есть опубликованная документация и OpenAPI, при запросе можно передать название, исполнителя, альбом и длительность; ответ TTML/QRC/LRC несет подлинные интервалы текста. Сначала стоит добавить его отдельным источником на ограниченный один вызов и пропускать результат через уже существующую строгую identity/version/duration-проверку. API-документация говорит, что cache-hit доступен без ключа, а miss может вернуть `401`; это должен быть обычный provider miss, не причина блокировать каскад. Ссылки: [официальный quick start и параметры](https://docs.betterlyrics.org/), [официальный OpenAPI reference](https://docs.betterlyrics.org/reference/openapi), [форматы и провайдеры](https://docs.betterlyrics.org/docs/providers).
2. **Для точного выбора версии / официального видео полезна Better Lyrics Unison**, особенно если известен YouTube video ID. Её публичный API возвращает метаданные, длительность, формат, тип синхронизации и community confidence; можно делать точный lookup по song+artist(+album/duration) либо поиск кандидатов и явно отбирать нужный `videoId`. Но не следует автоматически брать первый поисковый результат для remix/slowed/live: сначала проверить metadata, version и duration, а при неоднозначности получить варианты/показать выбор. Ссылки: [Unison API guide](https://docs.betterlyrics.org/unison), [документация API и matching](https://github.com/better-lyrics/unison).
3. **SimpMusic Lyrics технически интересен как community DB с настоящими word-level timestamps**, но найденный официальный клиент читает записи только по YouTube `videoId`; в коде нет title-search endpoint, а отдельной публичной API-документации/контракта вне исходников не найдено. Как дополнительный source для NeDotify он хорош только там, где есть подтверждённый YouTube ID этой версии. Не подключать с перебором/угадыванием ID.
4. Пословное/послоговое выделение требует хранить и рендерить структуру `(line, words[], start, end)`. Простое изменение скорости highlight внутри обычной LRC-строки будет визуальной имитацией, а не синхронизацией. Сейчас NeDotify работает с LRC line timestamps; её seek и сдвиг строковой синхронизации уже пригодны для этой модели, но word-level данные и рендерер нужно добавить отдельно.

## Как устроены форматы и настоящее word timing

| Формат | Что реально хранит | Практическое следствие |
|---|---|---|
| LRC / enhanced LRC | Обычный LRC ставит время на строку. Enhanced LRC может вложить метки времени для фрагментов/слов, но провайдеры и парсеры по-разному его поддерживают. | Из обычной LRC нельзя вывести время произнесения каждого слова. Синтетическое равномерное распределение по символам лишь маскирует отсутствие данных. |
| TTML | XML с началом/концом timed span; в Better Lyrics API провайдер TTML документирован как syllable-synced. AMLL парсит в линии и слова с временными границами. | Лучший путь для близкого к Apple Music karaoke highlight, если API реально вернул word/syllable spans. Проверять результат, так как XML может быть line-sync. |
| QRC | QQ line + word intervals `(start,duration)`. AMLL parser преобразует каждую временную пару в start/end слова. | Подлинный word timing, когда он есть; подходит для замены на fallback-provider, но не гарантирует покрытие конкретного трека/языка. |
| YRC | Netease line + word intervals `(start,duration,0)`. | Тоже подлинный word timing. AMLL поддерживает parsing, но YRC не следует приписывать LRCLIB или обычному LRC-источнику. |
| SimpMusic Rich Sync | Подстрока с timestamp перед каждым словом (`<MM:SS.mm>word...`) и отдельные границы строки. | Код явно собирает реальные word start times; если rich sync не парсится, SimpMusic возвращается к line-synced отображению. |

AMLL кодирует линию как `words: LyricWord[]`; документация типа прямо говорит, что для line-only LRC строка будет представлена одним «словом». Это исключает выдачу line timing за word timing. Реализация и парсеры находятся в [AMLL types.ts на 5fee356](https://github.com/amll-dev/applemusic-like-lyrics/blob/5fee356362353dbb24ce9bea3a62536478040de7/packages/lyric/src/types.ts), [TTML parser](https://github.com/amll-dev/applemusic-like-lyrics/blob/5fee356362353dbb24ce9bea3a62536478040de7/packages/lyric/src/formats/ttml.ts), [QRC parser](https://github.com/amll-dev/applemusic-like-lyrics/blob/5fee356362353dbb24ce9bea3a62536478040de7/packages/lyric/src/formats/qrc.ts), [YRC parser](https://github.com/amll-dev/applemusic-like-lyrics/blob/5fee356362353dbb24ce9bea3a62536478040de7/packages/lyric/src/formats/yrc.ts), [LRC parser](https://github.com/amll-dev/applemusic-like-lyrics/blob/5fee356362353dbb24ce9bea3a62536478040de7/packages/lyric/src/formats/lrc.ts).

## Сравнение исследованных проектов

### Better Lyrics — получение и показ, база Unison, отдельный metadata API

**Исходная реализация расширения** строит параметры провайдеров из `song`, `artist`, `duration`, `album` и `videoId`; несколько источников сводятся в общую структуру lyric lines + parts. Unison lookup передаёт как video ID, так и текстовые метаданные и длительность. Результат имеет `format: ttml|lrc|plain`, `syncType: richsync|linesync|plain`. При TTML вызывается `fillTtml`, для LRC различие word-synced/ordinary-synced берётся из `syncType`. Это хорошая схема различать точность данных, а не угадывать её по анимации: [providers/unison.ts на 028724f](https://github.com/better-lyrics/better-lyrics/blob/028724fa4b8a95a2949795c631c6ed3e88f82aa1/src/modules/lyrics/providers/unison.ts), [общая типизация/роутинг источников](https://github.com/better-lyrics/better-lyrics/blob/028724fa4b8a95a2949795c631c6ed3e88f82aa1/src/modules/lyrics/providers/shared.ts), [TTML адаптер](https://github.com/better-lyrics/better-lyrics/blob/028724fa4b8a95a2949795c631c6ed3e88f82aa1/src/modules/lyrics/providers/ttmlSource.ts).

**Unison API.** Документация описывает GET `/lyrics?v=<videoId>`, lookup по `song` и `artist` с необязательными `album`/`duration`, а также `/lyrics/search`. Query `song+artist` возвращает полные записи; поисковый `/lyrics/search?q=` предназначен для discovery и отдаёт ранжированные кандидаты, у которых далее нужно выбрать запись/ID. Есть список вариантов на video ID. В ответе есть фактические `videoId`, `song`, `artist`, `album`, `duration`, `format`, `syncType`, `confidence`, `lyrics`. API rate limit — 120 чтений/минуту/IP; для NeDotify это всё равно следует вызывать максимум один раз на fallback source, без fan-out кандидатов за UI. Не нужно передавать пользовательский input как «official», пока record не сопоставлен с конкретным stream/version. Источники: [read/search/variants и поля ответа](https://docs.betterlyrics.org/unison), [Unison implementation на 028724f](https://github.com/better-lyrics/better-lyrics/blob/028724fa4b8a95a2949795c631c6ed3e88f82aa1/src/modules/lyrics/providers/unison.ts); в extension production URL вынесен в [constants.ts](https://github.com/better-lyrics/better-lyrics/blob/028724fa4b8a95a2949795c631c6ed3e88f82aa1/src/core/constants.ts).

**Better Lyrics API.** Это отдельный сервис от Unison и отдельный кандидат. Официальный API принимает название, исполнителя, альбом и duration в секундах. TTML default обещает syllable timing, Kugou даёт line LRC, QQ возвращает QRC word timing. Docs публикуют OpenAPI на `https://api.betterlyrics.org/openapi.json`. Документация прямо оговаривает условность бесплатного доступа: cache hits доступны без API key, а для miss, не имеющегося в cache, может понадобиться key (`401`). Для сети рекомендую один запрос к `/getLyrics` на lookup; не делать все TTML/QQ/Kugou параллельно. При miss, невалидном TTML, недостаточных spans, непрохождении metadata gate — переходить дальше. Ссылки: [API guide](https://docs.betterlyrics.org/), [provider matrix](https://docs.betterlyrics.org/docs/providers), [OpenAPI docs](https://docs.betterlyrics.org/reference/openapi). API отдельный от кода extension, поэтому текущий extension код нельзя считать его контрактом; контракт — опубликованная документация/OpenAPI.

### AMLL — renderer и parsers, не источник текстов

AMLL даёт пригодную схему отображения, но сам по себе не является lyrics search service. В parsed model слово имеет `startTime` и `endTime`; строки и слова валидируются на конечный неотрицательный timestamp и `start <= end`. React компонент получает playback `currentTime` извне и вызывает `setCurrentTime(currentTime, isSeeking)`; базовый player получает миллисекунды и отдельно обозначенный seek. Указано, что точность/частота push от host влияет на отзывчивость. На каждом кадре `update()` продвигает анимации; seek принудительно помечается, чтобы синхронизация и скролл перестроились на target time. Ссылки на исходники [core base player на 5fee356](https://github.com/amll-dev/applemusic-like-lyrics/blob/5fee356362353dbb24ce9bea3a62536478040de7/packages/core/src/lyric-player/base/index.ts), [React player bridge](https://github.com/amll-dev/applemusic-like-lyrics/blob/5fee356362353dbb24ce9bea3a62536478040de7/packages/react/src/lyric-player.tsx), [timestamp validation](https://github.com/amll-dev/applemusic-like-lyrics/blob/5fee356362353dbb24ce9bea3a62536478040de7/packages/core/src/utils/validate-lyric.ts).

Что перенять в NeDotify: хранить отдельный флаг `syncType`; line-synced lyrics остаются текущими строками; word/syllable spans рендерить внутри строки, переключая классы/маску по `currentPosMs + userOffsetMs`. Подключать clock из playback host — не локальный таймер, который сам считает время, потому что он разойдётся после pause, seek, buffering, rate change или смены stream. При click на строку/слово seek нужно делать по соответствующему `startMs`. Для задержки аудиовыхода хранить индивидуальный offset отдельно от lyric timestamps; не изменять загруженные исходные данные.

### SimpMusic — rich sync и community lyrics, YouTube-ID bound

В актуальном SimpMusic desktop/mobile клиент вызывает `getSimpMusicLyrics(videoId)`, затем использует community запись; при miss переходит на Spotify/LRCLIB. В заявленной архитектуре endpoint связывает запись с YouTube ID; контракт, доступный в checked source, не содержит поиска по title/artist. API URL клиента — `https://api-lyrics.simpmusic.org/v1/`; `GET /v1/{videoId}`. Запись хранит `videoId`, а не обычную title/version query. Источники: [SimpMusic client code на 2be4b24](https://github.com/maxrave-dev/SimpMusic/blob/2be4b24b2c96fb2a3035f88350892e2721bec42f/composeApp/src/commonMain/kotlin/com/maxrave/simpmusic/viewModel/SharedViewModel.kt) и pinned submodule [core/SimpMusicLyrics.kt на f4de76a](https://github.com/maxrave-dev/core/blob/f4de76a88ab1b50c55eec2092ea1f564845df148/service/lyricsService/src/commonMain/kotlin/org/simpmusic/lyrics/SimpMusicLyrics.kt). Текстовая структура использует rich-sync `<MM:SS.mm>`-метки перед словами; парсер превращает их в start times и line boundaries: [RichSyncParser.kt на 2be4b24](https://github.com/maxrave-dev/SimpMusic/blob/2be4b24b2c96fb2a3035f88350892e2721bec42f/composeApp/src/commonMain/kotlin/com/maxrave/simpmusic/extension/RichSyncParser.kt). UI подсветки и seek использует playback position с отдельным user offset: [AppleMusicLyricsView.kt](https://github.com/maxrave-dev/SimpMusic/blob/2be4b24b2c96fb2a3035f88350892e2721bec42f/composeApp/src/commonMain/kotlin/com/maxrave/simpmusic/ui/screen/player/content/applemusic/AppleMusicLyricsView.kt), [offset settings в pinned core DataStoreManager](https://github.com/maxrave-dev/core/blob/f4de76a88ab1b50c55eec2092ea1f564845df148/domain/src/commonMain/kotlin/com/maxrave/domain/manager/DataStoreManager.kt).

SimpMusic документирует собственные community contributions/voting и несколько provider fallback, но сам по себе факт перевода трека на русский не означает существование русской community-записи. Не обещать RU покрытие. В сравнении для общего title-based NeDotify lookup он уступает Better Lyrics API/Unison из-за video ID requirement. Если трек NeDotify имеет YouTube ID, запрашивать только его, проверять ID, timestamp/duration ranges, network timeout/response-size и возвращаться к общему каскаду на miss.

### syncedlyrics — агрегатор провайдеров, не новый источник

`moehmeni/syncedlyrics` — Python-агрегатор LRCLIB, Netease, QQ, Musixmatch, Deezer и др.; общий интерфейс выбирает synced/plain и умеет попросить enhanced lyrics, но в коде надо внимательно смотреть конкретный provider. `enhanced=True` маршрутизируется в Musixmatch richsync; это уже подлинные word markers, если источник их выдал. Общая функция вызывает провайдеров по очереди, обновляет лучший найденный результат, но держит внутреннюю fuzzy text matching политику; для NeDotify её нельзя использовать как замену строгому `accept`/duration/version gate. Дополнительная зависимость также дублирует часть LRCLIB/Netease/QQ/Musixmatch запросов. Не рекомендую подключать пакет целиком поверх текущего cascade; полезнее заимствовать идею конкретного bounded source или формат-парсер (с учётом лицензии), сохраняя свой матчинг. Источники: [search orchestration на 3c8a318](https://github.com/moehmeni/syncedlyrics/blob/3c8a318d9a8df26855bdc3a5d23f7fd2b99ade2e/syncedlyrics/__init__.py), [Musixmatch provider](https://github.com/moehmeni/syncedlyrics/blob/3c8a318d9a8df26855bdc3a5d23f7fd2b99ade2e/syncedlyrics/providers/musixmatch.py), [LRCLIB provider](https://github.com/moehmeni/syncedlyrics/blob/3c8a318d9a8df26855bdc3a5d23f7fd2b99ade2e/syncedlyrics/providers/lrclib.py).

## Рекомендация по NeDotify

- Следующий потенциальный provider проверить на staging/local fixtures: **Better Lyrics API `/getLyrics`**, строго после существующих lyric metadata cleanup/version forms и после текущих providers или как ранний кандидат только при подходящей длительности/варианте. Начать с одного bounded GET и TTML parse; никаких одновременных retries по трём сервисным route. При недоступном API/key — обычный miss. Проверить `ttml` структуру/metadata; если API response не предоставляет идентифицируемого metadata, принимать только через сопоставление входной query с ожидаемой version и подтверждение TTML content metadata, если оно есть; иначе не ослаблять текущую проверку ради большей заполненности. Публичные docs описывают response как `{ttml}`, то есть не надо предполагать, что endpoint возвращает title/artist/duration отдельно.
- Если есть YouTube video ID, отдельно рассмотреть **Unison** как source с подтверждаемым `videoId` и `confidence`; обязательно перепроверять `data.song`, `artist`, `album`, `duration`, format/sync type. Search endpoint — максимум один query, получать lyrics только выбранной записи. Это лучший механизм выбора source edition, чем title search без исходного track ID, но не всегда источник availability.
- Для word karaoke сначала расширить data contract Python→JS, не модифицируя или распределяя line timestamp на буквы. Принимать parsed TTML/QRC как реальные word spans, `syncType=linesync` как текущий line highlight. Playback position, seek и offset должны оставаться едиными миллисекундами; offset применяется к playback position при выборе активного интервала, но исходные spans не переписываются. Рекомендую линейный проход по короткому массиву spans или бинарный поиск активного интервала; при каждом tick не перестраивать DOM/geometry без изменения активного span.
- RU покрытие оценивать по telemetry/ручным результатам под набор реальных русских каталогов, не по языку API/репозитория. Для каждого кандидата держать Cyrillic original query, альтернативную транслитерацию как отдельный bounded query только при miss, затем строгую проверку исполнителя, версии, duration, плюс описание совпавшего издания. Любой API/community DB может не иметь lyric для конкретного ремикса; ни один из исследованных source не даёт гарантии полного русского каталога.

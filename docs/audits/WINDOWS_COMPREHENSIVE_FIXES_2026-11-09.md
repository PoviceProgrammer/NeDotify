# NeDotify Windows — проверка и исправления 2026-11-09

## Область и достоверность результата

Работа выполнена только в `NeDotify_Windows`. Исходники Android/Linux не менялись. Незакоммиченные изменения, существовавшие до этой работы, сохранены; общий `git diff` включает и их, поэтому он не является списком только данного аудита.

Исправления подтверждены автоматическими регрессионными проверками, реальными сетевыми запросами и отдельным запуском настоящего WebView2 с живым аудиопотоком. Виртуальной машины с чистой Windows и компилятора Inno Setup в окружении нет. Реальные UAC, установка/загрузка драйвера WinDivert и обход DPI не выполнялись. Эти ограничения не заменяются успешными моками.

## 1. Zapret: найденные причины и исправления

### Первый запуск установленного приложения

**Причина.** `installer.iss` допускает выпуск без вложенного пакета Zapret. `download_binaries()` скачивал официальный закреплённый архив в `~/.nedotify/zapret`, но `_protected_elevation_path()` запрещает запуск из этого каталога через UAC. В результате предусмотренный приложением путь первого включения без администратора упирался в собственный запрет. Повторная установка такого же установщика не исправляла ситуацию. Кроме того, копия в профиле выбиралась раньше установленной.

**Исправление, `services/zapret_service.py`.** `_binary_directory()` выбирает `{app}/zapret` исключительно для frozen-приложения, чей каталог совпадает с `InstallLocation` установщика и содержит запускаемый `NeDotify.exe`. Архив по-прежнему проверяется закреплённым SHA-256 **до** распаковки. Установленная копия приоритетнее старой копии профиля. Предыдущая неудачная загрузка или неполный пакет исправляются повторной проверенной загрузкой, без копирования произвольных файлов из профиля в каталог повышения прав. Запуск не продолжается после неудачного скачивания.

В установленном пакете до замены проверяются `winws.exe`, `WinDivert.dll`, `WinDivert64.sys`, `cygwin1.dll` и PE-структура всех извлекаемых файлов. Неполный пакет не заменяет рабочие файлы. Существующая транзакционная распаковка/откат сохранены. Состояние PID, аргументы и версия остаются в пользовательском профиле. Комментарий `installer.iss` приведён в соответствие с этим поведением.

**Граница безопасности.** Правила `_protected_elevation_path()` не ослаблены. Portable/source-сборка без подтверждённой установки не получает новый разрешённый каталог. Как и до изменений, установка на пользователя сама по себе не делает её каталог недоступным для записи этому пользователю; прежнее ограничение TOCTOU сохраняется. Если ACL каталога установки не позволяет загрузку, операция завершается ошибкой; автоматического изменения ACL или отключения защиты нет.

### Честный статус и повторные команды

**Причины.** Успешный `ShellExecuteW` с пустым журналом считался доказательством работающего Zapret даже без обнаруженного PID. `is_running()` возвращал предположение как факт. Кеш статуса мог пережить переключение, а уже выполняющаяся сетевая проверка — записать старое `running=True` после остановки. Одновременная инвалидация могла также вызвать `dict(None)`. Старый отклонённый путь отравлял последующую попытку с очищенной настройкой.

**Исправления.** Неопределённый PID означает ошибку подтверждения и `state_unknown`, а не успешное включение. Отдельный флаг блокирует повторный запуск второго экземпляра. Если PID не удалось найти и при остановке, успешная остановка не заявляется; сообщение направляет к проверке диспетчера задач перед перезапуском. Отклонённый путь сбрасывается при новом поиске. После start/stop кеш инвалидируется под общим lock; `_status_epoch` и generation запрещают публикацию устаревшего результата фонового builder. Копия ответа `get_status()` снимается под lock.

### Выключение и позднее падение процесса

**Причины.** Обычный процесс приложения не мог завершить elevated winws через обычный `taskkill`; запроса UAC при выключении не существовало. Наблюдение за detached-процессом после UAC отсутствовало. Повторный start увеличивал generation и мог лишить уже запущенный процесс наблюдателя. В Popen-пути событие падения также оставляло прежний кеш статуса.

**Исправления.** `stop_interactive()` используется только кнопкой выключения через `AppApi.toggle_zapret`. При недостатке прав он может запросить UAC для системного `taskkill.exe`, ограниченного проверенным собственным PID и именем образа. При отказе/неудаче pidfile сохраняется, интерфейс получает реальную продолжающуюся работу процесса. Обычный `stop()` при выходе и фоновых операциях не вызывает новый UAC. Общий `_ensure_lifecycle_watcher()` восстанавливает наблюдение для Popen и detached PID после повторных команд; позднее падение сбрасывает состояние/кеш и передаёт `zapret_crashed` в существующий канал UI. Устаревший наблюдатель не очищает файлы нового поколения.

**Важное ограничение.** При нормальном выходе из приложения, запущенного без администратора, elevated winws может остаться работающим, если обычных прав остановки не хватает. Выход намеренно не показывает неожиданный UAC. Этот случай сообщается существующим механизмом `zapret_still_running`; собственный pidfile позволяет последующее обнаружение. Явное выключение перед выходом использует интерактивную остановку с UAC.

### Ожидаемая цепочка после исправлений

1. Переключатель блокирует повторные действия и вызывает `toggle_zapret` через публичный мост.
2. Валидируются режим/аргументы и находится либо скачивается проверенный пакет.
3. В установленной версии пакет находится в каталоге, допустимом существующим UAC gate.
4. Выполняется обычный запуск; при `winerror=740` или подтверждённой ошибке прав драйвера используется штатный запрос UAC.
5. Отмена UAC даёт понятную ошибку, `running=False`, без сохранённого ложного включения. Можно повторить действие.
6. Успех обычного запуска подтверждается живым процессом и окном выживания; elevated запуск требует атрибуции PID. Дальнейшее завершение отслеживается.
7. Мост сохраняет `zapret.enabled` по фактическому `is_running()`, и UI использует `running`, а не оптимистическое положение переключателя.
8. Статус процесса и доступность домена не объявляются доказательством действующего обхода DPI.

## 2. «Для тебя»

**Причина.** Настоящий блок главной использует `get_home_mixes`, а не только `get_feed`. Оба пути добавляли знакомые треки; первым миксом становились «Любимые и знакомые», а дневные подборки дополнялись библиотекой. Квоты ranking не исключали это при малом числе новых кандидатов. Кеш также мог вернуть уже знакомые записи после новых прослушиваний.

**Исправление.** В существующих режимах balanced/discovery исключаются известные записи, в том числе совпадения между провайдерами. История, лайки, плейлисты и музыкальные признаки остаются сигналами вкуса, но не подставляются вместо новой подборки. Режим familiar сохранён как явный выбор пользователя; его локальная/offline-подборка продолжает работать. При сбое внешнего источника стандартная подборка не маскирует ошибку старой библиотекой. Кеш и настоящая цепочка главной покрыты тестами. Пустой профиль использует существующую обработку cold start; персонализация без сигналов не обещается.

**Файлы и проверки.** `services/recommendation_service.py`, `ui/web_new_v2/js/home.js`, новые `tests/test_windows_discovery_album_regressions.py`, обновлённые recommendation/riff tests. Подробности, исключения и реальные ограничения — в [тематическом отчёте](windows-recommendations-albums-2026-11-09.md).

## 3. Пользовательские упоминания Яндекс Музыки

Удалены скрытый DOM авторизации, инструкции токена/device code, JS-обработчики и уведомления, публичный `yandex_device_auth` в `core/api.py`/`core/bridge.py`, источник из общего и явно запрошенного поиска, актуальные упоминания README/UI-документации. Общие элементы других сервисов сохранены.

**Осознанные исключения.** Backend и пакет `yandex_music`, hidden import, обработка сохранённых source ID/потоков/обложек, домены proxy/Zapret и маскирование старых секретов оставлены ради уже существующей библиотеки. Удаление этого кода лишило бы сохранённые треки воспроизведения и могло бы раскрыть старые токены. Исторические отчёты/миграции не переписывались. Поэтому буквальное отсутствие всех вариантов слова в Windows-репозитории не заявляется. Полный список причин и файлов — в [отчёте источников](windows-providers-lastfm-2026-11-09.md).

Поиск, поддерживаемые импорты, queue/playback/downloader и сборочные контракты проверены suites; настоящий download целого файла в нативном окне не выполнялся.

## 4. Last.fm: назначение и рекомендация

Last.fm оставлен. Это необязательный источник похожих исполнителей/треков, тегов и публичных chart/top-кандидатов для рекомендаций/метаданных. При настроенном username используются внешние top artists. Работа защищена opt-in/наличием ключа; локальная история и статистика хранятся в SQLite независимо от него.

Подтверждённые исходящие параметры: название/исполнитель запрошенной композиции, имя пользователя для внешнего топа и API-ключ самому Last.fm. Найденные вызовы не отправляют локальные аудиофайлы, лайки или локальную историю; scrobbling (`track.scrobble`, `updateNowPlaying`) не реализован. Прежнее обещание «ключи API не передаются» исправлено в настройках. Локальный топ переименован из `Local Last.fm` в «Топ треков».

Удаление снизит число внешних кандидатов и уберёт соответствующие metadata fallback; механическое удаление модуля сломает текущие импорты. **Рекомендация: оставить необязательным.** Все восемь вопросов, реальные методы, ограничения, consent-тесты и исправленный metadata fallback разобраны в [отдельном отчёте](windows-providers-lastfm-2026-11-09.md). С реальным ключом пользователя запросы не выполнялись.

## 5. Альбомы и релизы

**Причины.** Установленный ytmusicapi отбрасывал локализованную категорию «Альбомы» при сравнении с английским фильтром. Ключ кеша идентичности исполнителя не включал channel IDs; достоверное совпадение ID могло отвергаться из-за другого display name. Треклист не удалял повторы video ID. Метаданные каталога терялись до окна альбома, и UI оставлял устаревшие название/год/обложку.

**Исправления.** Язык протокольного SDK-клиента — `en`, регион RU и русский интерфейс сохранены. Исправлены identity/cache, дедупликация и передача подтверждённых метаданных всех каталогов; Deezer сохраняет дату/год/тип релиза/обложку. `openAlbumModal()` обновляет сведения после настоящего ответа, включая single/EP/compilation; ошибки и временная недоступность не выдаются за «не найдено».

**Файлы.** `services/youtube_service.py`, `catalog_service.py`, `deezer_service.py`, `ui/web_new_v2/js/search.js`, новые album regressions. Live-контроль до изменения: YouTube 0 альбомов; после — 20. Альбом Parachutes открыт через YouTube, Apple/iTunes и Deezer: по 10 треков с длительностью, подтверждённые метаданные и быстрый повтор из кеша. Один временный Apple timeout честно отработал ошибкой; повтор прошёл. [Финальный JSON](windows-album-live-final-2026-11-09.json).

## 6. Источники и воспроизведение

**Реальный Spotify отсутствует.** `SpotifyService` — историческое имя адаптера iTunes. Метаданные поступают из Apple/iTunes, звук ищется на YouTube с проверкой соответствия записи. UI/tooltip теперь говорят об этом прямо; внутренний `spotify` сохранён для совместимости. Импорт Spotify URL не реализован — новая фиктивная интеграция не добавлялась.

**Исправленная ошибка сопоставления.** `TrackResolver` терял expected_duration при раннем локальном поиске, поэтому принимал одноимённую запись 300 секунд вместо 180. Длина теперь проходит через существующий comparator, включая DatabaseManager/raw SQLite Row/tuple. Новые тесты сначала падали и затем прошли.

**Live.** YouTube предоставил HTTP206/audio bytes; ветка iTunes → verified YouTube также дала поток. Неподходящая часовая запись была отклонена вместо подстановки. SoundCloud подтвердил HLS manifest и media segment `audio/mp4`, HTTP206; 30-секундный preview корректно отвергнут как полный трек. DRM не обходился. Санитизированные JSON/воспроизводимый стенд перечислены в [отчёте источников](windows-providers-lastfm-2026-11-09.md).

**Нативное окно.** В пустом временном профиле, без подмены провайдеров, реальный WebView2 открыл Parachutes (10 треков, обложка), кнопка Play создала очередь на 10 треков, декодер воспроизводил поток. Проверены продвижение аудиочасов, пауза реальной кнопкой UI, остановка часов в паузе, продолжение, seek на 30 секунд и следующий трек. Аудиовыход был muted; слышимость не проверялась. [Результат](../../tools/bench/results/windows-native-live-20261109-171232/result.json), [снимок](../../tools/bench/results/windows-native-live-20261109-171232/native-album-player.png), стенд `tools/bench/check_windows_live_native_20261109.py`.

Первый запуск стенда не создал каталог БД; второй ошибочно использовал legacy `api.play_pause`, который по контракту только возвращает состояние. Стенд исправлен на действительную кнопку UI, последняя проверка прошла. Это ошибки тестового стенда, не изменения рабочего алгоритма паузы приложения.

## 7. Сводка регрессий, сборка и ограничения

**Финальный общий прогон после всех production-исправлений: 2805 passed, 9 skipped, 2 network deselected, 131.57 секунды.** Команда: `& '.venv_win\Scripts\python.exe' -m pytest -q --tb=short --durations=15`; полный вывод — `.test_runs/windows-comprehensive-verified-20261109.txt`. Из девяти skip восемь относятся к отсутствующему дереву Android в Windows checkout, один — отсутствующему историческому `CLAUDE.md`. Они не являются проверкой Android; его код не затрагивался. Предшествующие четыре падения старых expectations/промежуточного album fixture устранены и зафиксированы в `.test_runs/windows-comprehensive-20261109.txt`. Промежуточный общий прогон до двух дополнительных lifecycle regressions и трёх bridge-сценариев: 2800 passed, 116.46 секунд.

Общий pytest охватывает главную, библиотеку/плейлисты, поиск, исполнителей/альбомы, историю/сигналы, queue, resolver, recovery/истечение URL, скачивание, proxy/socket, настройки, bridge/thread safety, frontend JS и build contracts.

### P2-01 — The playback queue snapshot rewrites the entire settings DataStore every 5 seconds [MERGED x3]

* **Area:** AN-03 (PlaybackService) · AN-05 (queue) · AN-16 (preferences) · **Found by:** B in all three
* **Files:** `android/app/src/main/java/ru/nedotify/app/player/PlaybackService.kt:183-186`, `:333-342`; `android/app/src/main/java/ru/nedotify/app/data/Preferences.kt:38`, `:49`; `android/app/src/main/java/ru/nedotify/app/NeDotifyApp.kt:24-31`
* **Status:** CONFIRMED (the DataStore `PreferencesSerializer.writeTo` behaviour was read from the shipped 1.2.0 AAR)
* **Description.** The queue checkpoint is stored **in the settings DataStore** under `queue_v1` as a JSON blob. `checkpointQueue()` is called from a 5-second timer while playing **and** on every `EVENT_POSITION_DISCONTINUITY` (i.e. every seek). The snapshot embeds `player.currentPosition`, so the de-duplication guard `if(snapshot!=lastCheckpoint)` can never suppress a write while anything is playing. Each write makes DataStore re-serialise and atomically rewrite the **whole** preferences protobuf.
* **Cause.** Session state (the queue) was placed in the same key/value file as the user's settings, and the checkpoint cadence was chosen to preserve the playback position — which changes on every tick — so the "did anything change?" comparison includes the one field that always changes.
* **Trigger.** Any playback: ~12 whole-file writes per minute, ~720 per hour, plus one per seek.
* **User impact.** Sustained write traffic and fsync for the whole listening session, proportional to the queue size: with ~20-character track ids a 200-track queue is a ~5 KB blob and a 1000-track queue ~25 KB → roughly 60 KB/min and **18 MB/hour** of file writes, plus 720 fsyncs/hour. The JSON is also built and string-compared **on the main thread** (the service scope is `Dispatchers.Main.immediate`).
* **Evidence.**
```kotlin
// PlaybackService.kt:333-342
private fun checkpointQueue() {
    val ids=JSONArray((0 until player.mediaItemCount).map {player.getMediaItemAt(it).mediaId})
    val order=player.shuffleOrder
    val shuffled=mutableListOf<Int>();var index=order.firstIndex
    while(index!=C.INDEX_UNSET && shuffled.size<player.mediaItemCount){shuffled+=index;index=order.getNextIndex(index)}
    val snapshot=JSONObject().put("version",2).put("ids",ids).put("index",player.currentMediaItemIndex)
        .put("currentId",player.currentMediaItem?.mediaId).put("position",player.currentPosition)
        .put("repeat",player.repeatMode).put("shuffle",player.shuffleModeEnabled).put("shuffleOrder",JSONArray(shuffled)).toString()
    if(snapshot!=lastCheckpoint){lastCheckpoint=snapshot;app.saveQueue(snapshot)}
}
```
* **Reproduction.** Play with a 300-track queue and watch the mtime of `files/datastore/nedotify.preferences_pb` — it advances every 5 s and its size tracks the queue. Unit-level: two snapshots 5 s apart with identical ids/index/shuffle and a different `position` are unequal, so `saveQueue` is called twice.
* **Fix.** Separate the *queue shape* (ids, index, repeat, shuffle, shuffle order) from the volatile *position*: compare only the shape for the de-duplication decision, and persist the position on a slower cadence or only on pause/stop/transition. Better: move the snapshot out of the settings file entirely (a dedicated file or a Room table) so the settings file is not rewritten at all.
* **Fix side effects.** A slower position cadence widens the window in which an *ungraceful* process kill loses progress on resume; a separate small "position" preference key avoids that. Moving the blob out of DataStore changes `Preferences.queue()` and orphans the `queue_v1` key (old installs silently lose their restored queue once).
* **Note on prior art:** `android/review/REVIEW_RESOLUTION.md:45` claimed this fixed ("history и queue отбрасывают одинаковые снимки"). `ListeningHistory` *does* discard identical records; the **queue** snapshot never does, because the position is inside the compared value. **Partial fix of a previously-closed item.**
* **Desktop contrast:** `core/session.py:9,50-55` caps the persisted queue at 200 entries and writes once, at exit.

### P2-02 — `NeDotifyApp.audioCache` blocks the main thread for up to 1.5 s at every cold start [MERGED x3]

* **Area:** AN-01 (app shell) · AN-16 (preferences) · **Found by:** A and B in both
* **Files:** `android/app/src/main/java/ru/nedotify/app/NeDotifyApp.kt:20-23`; triggered from `android/app/src/main/java/ru/nedotify/app/player/PlaybackService.kt:53-56`; reached via `android/app/src/main/java/ru/nedotify/app/ui/MusicViewModel.kt:103-106`
* **Status:** CONFIRMED
* **Description.** `audioCache` is a `by lazy` whose initializer performs a **blocking** read of the DataStore on the calling thread:
```kotlin
val audioCache by lazy {
    val megabytes=runBlocking(Dispatchers.IO) {withTimeoutOrNull(1_500) {repository.audioSettings.settings.first().cacheLimitMb}?:256}
    SimpleCache(File(cacheDir,"audio"),LeastRecentlyUsedCacheEvictor(megabytes.toLong()*1024*1024),StandaloneDatabaseProvider(this))
}
```
`runBlocking` parks the **caller**. The only caller is `PlaybackService.onCreate`, which the framework runs on the **main thread**. Media3 binds with `BIND_AUTO_CREATE`, so the service is created as part of the first Activity launch — before the user has pressed play. Media3's `SimpleCache` constructor **also** blocks the calling thread for the whole cache-directory scan (`conditionVariable.block()`), which the XI-06 review confirmed from the 1.11.1 source.
* **Cause.** A lazily-initialised, `runBlocking`-based read of a persistent setting inside a main-thread `Service.onCreate`, combined with a controller bind that auto-creates the service.
* **Trigger.** Every cold start (and after every process death).
* **User impact.** A visible up-to-1.5 s UI freeze before the first frame is interactive, plus the `SimpleCache` construction (real disk I/O) on the same thread. Below the 5 s ANR budget, so it is jank rather than an ANR — but it lands on every cold start.
* **Reproduction.** `adb shell am start -W -n ru.nedotify.app/.MainActivity` and compare `TotalTime`; or enable `StrictMode` with `detectDiskReads()` on the main thread in a debug build and watch the `NeDotifyApp.audioCache` frame fire.
* **Fix.** Publish the limit asynchronously into a `@Volatile` field with a 256 MB default, and build the `SimpleCache` from that field. `LeastRecentlyUsedCacheEvictor` exposes `setMaxCacheSize`, so the real limit can be applied later without recreating the cache.
* **Fix side effects.** For the first seconds of playback the cache uses the default limit; a user whose limit is *smaller* briefly overshoots. A second background read is still required. Re-creating a `SimpleCache` over the same directory while the old one is alive trips Media3's "another SimpleCache instance uses the same directory" lock, so a re-create must release the previous instance first.
* **Note:** this is **not** the previously-rejected B P2-12. That rejection covered the claim that the `SimpleCache` *constructor* scans the directory on the main thread — the scan runs on Media3's own init thread, but the **constructor blocks the caller** for the whole scan, and the caller here is the main thread.

### P2-03 — The OAuth redirect and the pending PKCE login are consumed before the token exchange succeeds [MERGED x4]

* **Area:** AN-01 (app shell) · AN-09 (provider auth) · **Found by:** A and B in both
* **Files:** `android/app/src/main/java/ru/nedotify/app/MainActivity.kt:29-38`; `android/app/src/main/java/ru/nedotify/app/data/ProviderConnections.kt:93-105`
* **Status:** CONFIRMED
* **Description.** Two independent losses stack:
  1. `MainActivity.readOAuth` dispatches the redirect into an in-memory coroutine and then **immediately** clears `intent.data`, so the payload exists nowhere but in a process-bound coroutine:
```kotlin
private fun readOAuth(intent:Intent) {
    val uri=intent.data?:return
    if(uri.scheme=="nedotify" && uri.host=="oauth" && uri.path=="/spotify")model.handleSpotifyRedirect(uri.toString())
    intent.data=null
}
```
  2. `ProviderConnections.handleSpotifyRedirect` **deletes** the single-use `spotify_pending` record (which holds the PKCE verifier) **before** the token exchange:
```kotlin
store.remove("spotify_pending");pending=null
val body=FormBody.Builder().add("client_id",clientId).add("grant_type","authorization_code")
    .add("code",code).add("redirect_uri",AuthPkce.REDIRECT).add("code_verifier",awaiting.verifier).build()
val received=ProviderToken.response(network.json(Request.Builder().url(endpoints.spotifyToken).post(body).build()),now())
```
  A transient failure at the token endpoint (no connectivity, captive portal, a 5xx — the call timeout is 30 s) therefore destroys **both** the authorization code and the verifier, with no retry path.
* **Cause.** Single-use is implemented by *deleting* the pending rather than by *consuming* it, and consumption happens before the one step that can still fail for reasons unrelated to the user's intent.
* **Trigger.** Any transient failure of `POST https://accounts.spotify.com/api/token`; or a process kill during the exchange window (the `onCreate` guard `if(savedInstanceState==null)` skips a re-read on a recreated Activity).
* **User impact.** The user completes the Spotify sign-in in the browser, returns to the app, and is told the login failed. The consent grant is thrown away and the whole browser round-trip must be repeated. After a process kill the loss is **silent** — no message at all.
* **Reproduction.** Put the device behind a proxy that returns 503 for `accounts.spotify.com/api/token` but 200 for `accounts.spotify.com/authorize`; complete the authorisation; observe the failure and that a second attempt without restarting the login yields «Нет активного входа Spotify».
* **Fix.** Keep the pending record (and the verifier) until the exchange has *succeeded*, or has failed with a definitively non-retryable status (`invalid_grant`/400); a 5xx/timeout should leave it intact. On the Activity side, stop nulling `intent.data` unconditionally, and replace the `savedInstanceState == null` guard with an explicit "already consumed" marker — the encrypted store already holds the single-use pending and can be the source of truth.
* **Fix side effects.** Retaining the pending widens the replay window from "until the exchange starts" to "until the pending's 10-minute expiry"; a per-attempt "exchange already attempted" flag inside the pending record bounds it to one retry. A retry is safe only where the request provably never reached Spotify — the authorization code is single-use server-side.

### P2-04 — The exported `PlaybackService` accepts any Media3-"trusted" controller, and Media3's trust predicate includes "enabled notification listener" [MERGED x2]

* **Area:** AN-01 (app shell) · AN-03 (playback service) · **Found by:** B in both
* **Files:** `android/app/src/main/AndroidManifest.xml:29-32`; `android/app/src/main/java/ru/nedotify/app/player/PlaybackService.kt:85-105`
* **Status:** CONFIRMED — Media3's trust semantics established by `javap` decompilation of the exact pinned AAR (`media3-session:1.11.1`)
* **Description.** The service is exported with a `MediaSessionService` intent filter, so any app on the device can bind. `onConnect` is the only gate:
```kotlin
override fun onConnect(mediaSession:MediaSession,controller:MediaSession.ControllerInfo):MediaSession.ConnectionResult {
    return if(controller.packageName==packageName || controller.isTrusted)
        MediaSession.ConnectionResult.accept(MediaSession.ConnectionResult.DEFAULT_SESSION_COMMANDS,MediaSession.ConnectionResult.DEFAULT_PLAYER_COMMANDS)
        else MediaSession.ConnectionResult.reject()
}
```
`controller.isTrusted` is **not** a signature check. In Media3 1.11.1 it is true when the connecting UID is 1000 (system), the app's own UID, **or** the connecting package holds `STATUS_BAR_SERVICE`, **or** `MEDIA_CONTENT_CONTROL`, **or** is an *enabled notification-listener service*. `DEFAULT_PLAYER_COMMANDS` is `Player.Commands.Builder.addAllCommands()` — the complete set, including `COMMAND_SET_MEDIA_ITEM` and `COMMAND_ADD_MEDIA_ITEMS` — and `onPlayerCommandRequest` returns `RESULT_SUCCESS` unconditionally.
* **Precise residual risk.** A trusted third party **can**: read the Now-Playing metadata and the whole queue (media ids + titles — the user's listening history and library contents); drive transport; and replace, reorder, remove or clear the queue with any subset of tracks already in the Room library. It **cannot** inject a URI or an arbitrary media item — `onSetMediaItems`/`onAddMediaItems` discard the controller's `MediaItem`s except for `mediaId` and rebuild every item from the database row (`readQueue` → `selectQueue` → `dao.tracks(ids)` → `mediaItems(...)`); an id absent from the library is dropped, and an all-unknown list yields «В очереди нет доступных треков». It **cannot** reach the OAuth tokens, and it **cannot** spoof its package name (Media3 validates the package against the calling UID via `SessionUtil.checkPackageValidity` before `onConnect`).
* **Trigger.** The user installs an app and grants it notification-listener access (or the app holds `MEDIA_CONTENT_CONTROL`). That app binds and is accepted. No interaction inside NeDotify is required.
* **User impact.** Silent disclosure of what the user is listening to and of their library contents, and an external app taking over playback and the queue. Nothing inside NeDotify indicates that a third-party controller is connected.
* **Reproduction.** On an API 33+ device, install a minimal app that requests `NotificationListenerService` access, bind to `ru.nedotify.app/.player.PlaybackService` with a `MediaController`, and observe that the connection is **accepted**. Then call `setMediaItems` with an attacker URI and observe that the played URI is `nedotify://track/<id>`.
* **Fix.** Split the acceptance by controller identity: accept the full command set only when `controller.packageName == packageName`; for every other controller accept `DEFAULT_UNTRUSTED_SESSION_COMMANDS` / `DEFAULT_UNTRUSTED_PLAYER_COMMANDS` (read-only + transport), or reject outright. Consider logging/surfacing connected foreign controllers.
* **Fix side effects.** System controllers (Android Auto, Assistant, Wear, Bluetooth) would lose `COMMAND_SET_MEDIA_ITEM` and the ability to replace the queue. The app exposes no `MediaBrowser`/library service, so the loss is confined to queue replacement by external controllers — but it must be re-verified on a device with Android Auto and with a headset.

### P2-05 — One provider mutex is held across provider network I/O, so one slow provider stalls every other provider operation [MERGED x3]

* **Area:** AN-09 (provider auth) · AN-10 (catalog providers) · **Found by:** A and B in both
* **Files:** `android/app/src/main/java/ru/nedotify/app/data/ProviderConnections.kt:21` (the mutex), `:62-74` (`action`), `:103`, `:109-110`, `:135-139`
* **Status:** CONFIRMED
* **Description.** `ProviderConnections` serialises *all* provider state transitions through one `Mutex`, and `action` holds it across the block's body — including the HTTP calls made by `handleSpotifyRedirect` and `saveYandexToken`. The Spotify **token refresh** is likewise performed inside the lock. The same mutex is required by `get()`, `postYandex()`, `spotifyAccess()` and `yandexScope()` for every catalogue read and every Yandex stream resolution.
* **Cause.** The mutex is used simultaneously as the credential-state mutex, the single-flight refresh gate and the busy-flag gate, so it must be held across I/O that could be done outside it. The generation/`checkAccess` machinery at `:156-159` and `:183-191` already provides the consistency guarantee a network call outside the lock would need.
* **Trigger.** An expired Spotify token (roughly hourly) with a degraded or slow network; or any provider action while a login/logout is in flight. The OkHttp call timeout is 30 s.
* **User impact.** The catalogue dialog shows an indefinite spinner (up to 30 s) and the **unrelated Yandex** collection is blocked by a Spotify problem. A Yandex track transition and the download worker both block on the same lock, so they hit the 15 s `sourceDeadline` in `LibraryRepository.resolve` and fail with «Источник не ответил вовременить». The Settings panel disables **every** control (`enabled=!status.busy`).
* **Evidence.**
```kotlin
// ProviderConnections.kt:62-74
private suspend fun <T> action(block:suspend ()->T):T=withContext(Dispatchers.IO) {
    lock.withLock {
        _status.value=_status.value.copy(busy=true,error=null)
        try {load();block()}
        ...
        finally {publish();_status.value=_status.value.copy(busy=false)}
    }
}
// ProviderConnections.kt:135-139 — the refresh POST runs inside the lock
val response=try {network.json(Request.Builder().url(endpoints.spotifyToken).post(body).build())}
```
* **Reproduction.** `MockResponse().setSocketPolicy(SocketPolicy.NO_RESPONSE)` on the token endpoint, then start a second provider call (`session.spotify.search(...)`) and observe that it does not reach the server until the first call times out.
* **Fix.** Narrow the lock to the credential-state critical sections (read/compare/increment the generation) and move the HTTP work outside it, using a separate single-flight `Deferred` keyed by generation for the refresh — the same shape `SoundCloudClient` already uses in `data/Sources.kt:58-79`.
* **Fix side effects.** The current code is what guarantees "one refresh for N concurrent expired requests" (pinned by `ProviderConnectionsTest.kt:57-68`) and the generation fences that stop a stale response from repopulating a logged-out account (`:192-232`). Splitting the lock without an explicit single-flight primitive reintroduces both, so the replacement must be built and tested first. The `busy` flag must move out of the lock so it reflects the actual in-flight work.

### P2-06 — `startFlow()` permanently flips the user-visible "Продолжать музыку" setting and never restores it [MERGED x2]

* **Area:** AN-02 (ViewModel) · AN-16 (preferences) · **Found by:** B in both
* **Files:** `android/app/src/main/java/ru/nedotify/app/ui/MusicViewModel.kt:285-295` (line 292); `android/app/src/main/java/ru/nedotify/app/ui/AudioSettingsControls.kt:78-82`; `android/app/src/main/java/ru/nedotify/app/player/PlaybackService.kt:191-232`
* **Status:** CONFIRMED
* **Description.** `startFlow()` — a one-shot action on the Home screen — persists `AudioSettings.autoplay = true` into the `nedotify_audio` DataStore. `autoplay` is the *global* user preference «Продолжать музыку — Добавлять похожие треки, когда очередь заканчивается», and it drives the service's autoplay loop for **every** queue, not just the Flow queue. A repo-wide grep shows exactly one writer of `autoplay=true` and no writer of `autoplay=false` other than the Settings switch. The write happens *before* `playSelected`, so it persists even when the Flow fails to start.
* **Cause.** One persisted field serves two unrelated concepts — a transient action ("start a Flow now") and a persistent preference.
* **Trigger.** Any tap on the Flow card.
* **User impact.** After one tap, the Settings switch reads ON, every later queue auto-appends recommendations when it ends, across restarts, with no snackbar and no indication that a setting changed.
* **Evidence.** `MusicViewModel.kt:292` `repository.audioSettings.update {it.copy(autoplay=true)}`; `AudioSettingsControls.kt:82` the user-facing switch; `PlaybackService.kt:193` the global loop it enables. The desktop keeps them apart: `core/settings.py:72-74` has `"autoplay": False` **and** a separate `"flow_enabled": True`, and starting the desktop Flow (`core/api.py:4110 get_flow_tracks`) never mutates `autoplay`.
* **Reproduction.** Settings → Плеер → confirm the switch is OFF → Home → tap the Flow card → reopen Settings → the switch is ON and stays ON after a restart.
* **Fix.** Do not mutate the persisted preference from a one-shot action. Either pass "extend this queue" as a per-session argument to the service, or use a distinct persisted key (`flow_enabled`) mirroring the desktop.
* **Fix side effects.** A per-session flag means the Flow queue no longer survives a service restart; a separate key needs a default and a migration decision.

### P2-07 — The listening report is recomputed from SQL every 5–60 seconds while the profile screen is open, even when nothing changed [MERGED x2]

* **Area:** AN-02 (ViewModel) · AN-14 (discovery/reports) · **Found by:** B in both
* **Files:** `android/app/src/main/java/ru/nedotify/app/ui/MusicViewModel.kt:61-75`; `android/app/src/main/java/ru/nedotify/app/data/ListeningReports.kt:143-148`; `android/app/src/main/java/ru/nedotify/app/data/Models.kt:146-176`; `android/app/src/main/java/ru/nedotify/app/player/PlaybackService.kt:183-186`
* **Status:** CONFIRMED
* **Description.** Two independent refresh triggers fire the same six-statement aggregate:
  1. `reportClock` is a cold flow emitting every 60 s. It is combined with `reportRetry` and fed into an **inner** `flatMapLatest`, so every tick **cancels the current Room subscription and starts a new one**, which immediately re-runs `dao.reportSnapshot(window)`. The tick was meant to roll the local-day boundary; it re-subscribes every minute instead of only when the calendar day changes.
  2. `observe` is driven by `dao.observeReportChanges(SimpleSQLiteQuery("SELECT 1"))`, declared `@RawQuery(observedEntities = [ListeningSession::class, Track::class])`. The `history` table **is** `ListeningSession`, and the service writes a history checkpoint every 5 s while playing — so the whole snapshot is rebuilt every 5 s, not every 60 s. The 60 s clock is only the *idle* trigger.
  With `ReportPeriod.ALL` (`startInclusive = Long.MIN_VALUE`) four of the six queries scan the entire `history` table, and `dailyQuery()` evaluates a **365-branch `CASE`** per row (731 bound arguments — under SQLite's 999 limit, so valid but expensive).
* **Cause.** The invalidation signal is bound to the raw tables rather than to "the report window changed"; nothing throttles the recomputation, and the `ALL` window removes the natural time bound.
* **Trigger.** The Profile screen is open.
* **User impact.** With a year of history (~36 500 sessions) the `ALL` period costs ~13.3 M integer comparisons plus a temp B-tree `GROUP BY` over a computed expression, **four times over, every 5 seconds**. The report numbers do not change between ticks — the work is pure waste. Each emission also replaces the whole `ListeningReport` object, so the chart, the top lists and the history list are re-composed each time.
* **Evidence.** `Models.kt:147-148` the `@RawQuery`; `Models.kt:170-176` the six queries in one transaction; `ListeningReports.kt:66-82` the 365-branch `CASE`; `PlaybackService.kt:183-186` the 5 s history write. The desktop's report definition uses two **equal** rolling windows (`services/listening_comparison.py:23-24`).
* **Reproduction.** Open the Profile tab, select "Всё время", start playback, and watch the Room query log — the six queries re-execute every ~5 s with no user action.
* **Fix.** Decouple the refresh from the raw invalidation: observe a throttled "report epoch" and keep `reportRetry` as the explicit user trigger; make the clock emit only on a day rollover. For `ALL`, pre-aggregate per day instead of a 365-branch `CASE`.
* **Fix side effects.** A throttle means the "Минут прослушано" tile updates less often than the current ~5 s cadence. `ListeningReportsDaoTest.checkpointsAndTrackMetadataUpdateAnAlreadyCollectedReport` explicitly asserts that a `putSession` **immediately** updates an already-collected report, so that test must be relaxed or session-level freshness must be kept while throttling the expensive `ALL` queries.

### P2-08 — `importCatalog()` is an unbounded (worst case ~2 h 45 m), non-resumable batch of up to 1 000 sequential network round-trips [MERGED x2]

* **Area:** AN-02 (ViewModel) · AN-10 (catalog providers) · **Found by:** B in both
* **Files:** `android/app/src/main/java/ru/nedotify/app/ui/MusicViewModel.kt:369-394`; `android/app/src/main/java/ru/nedotify/app/data/CatalogMatcher.kt:66-76`; `android/app/src/main/java/ru/nedotify/app/data/Sources.kt:91-100`
* **Status:** CONFIRMED
* **Description.** The import takes up to 500 catalogue entries and resolves each **sequentially**; each resolution runs up to **two** provider searches serially under a 20 s `withTimeout` per item. Worst case `500 x 20 s ~ 2 h 46 m`; typical 8–25 minutes of sustained HTTPS traffic. The job runs in `viewModelScope` (`Dispatchers.Main.immediate`), so the SoundCloud JSON parse — 126 KB per response, `data/Sources.kt:91-100` returns a `String` and does **not** switch dispatcher — executes on the **main thread** once per item. There is **no** provider-response cache anywhere in the catalogue path, so re-importing the same playlist repeats every request; the desktop caches provider searches for 300 s (`services/base_service.py:132-135`). The Yandex path is unaffected: `YandexCatalog.playable` is a pure mapping with zero network calls.
* **Cause.** An unbounded-duration batch modelled as a UI-scoped coroutine instead of a persisted, resumable job — even though the codebase already has WorkManager for downloads.
* **Trigger.** Opening a Spotify/Yandex playlist with 200–1000 tracks and tapping "Импортировать список".
* **User impact.** The radio and CPU stay busy for tens of minutes. If the process is killed at item 400/500 **all** progress is lost, with no partial import, no resume and no record of what failed. Each parse is a main-thread stall.
* **Evidence.** `MusicViewModel.kt:377-383` the serial loop; `CatalogMatcher.kt:69` the serial two-provider loop; `CatalogBrowser.kt:52` the only control, disabled while working, with no cancel.
* **Reproduction.** Connect a Spotify account, open a >=200-track playlist, tap import, then `adb shell am force-stop` mid-way: no playlist is created and no error appears on the next launch.
* **Fix.** Move the batch into a WorkManager job with a persisted per-item progress table; bound the per-item timeout for the batch path; run the resolution on an IO dispatcher with bounded concurrency (2–4) instead of serially; add an explicit cancel control.
* **Fix side effects.** A WorkManager job needs foreground-service notification handling for long jobs and must re-initialise the provider connection across process restarts. Bounded concurrency raises the request rate and may trip provider rate limits.

### P2-09 — `runBlocking` inside the `ResolvingDataSource` pins a Media3 loader thread and makes the network resolution non-cancellable

* **Area:** AN-03 (PlaybackService) · **Found by:** B
* **Files:** `android/app/src/main/java/ru/nedotify/app/player/PlaybackService.kt:60-69`; `android/app/src/main/java/ru/nedotify/app/data/LibraryRepository.kt:76-83`
* **Status:** CONFIRMED (the Media3 1.11.1 cancellation semantics were read from the shipped AAR)
* **Description.** Media3's `ResolvingDataSource.Resolver` is **synchronous by contract**: `ResolvingDataSource.open()` calls `resolver.resolveDataSpec(dataSpec)` inline on the calling thread (AAR bytecode, no hand-off). The app bridges the suspend `repository.resolve(track)` with `runBlocking`:
```kotlin
val source=ResolvingDataSource.Factory(cached) {spec->
    if(spec.uri.scheme!="nedotify")spec else runBlocking {
        val track=repository.dao.track(spec.uri.lastPathSegment.orEmpty())?:throw SourceFailure("Трек отсутствует в библиотеке")
        val resolved=repository.resolve(track)
        ...
        spec.withUri(resolved.url.toUri())
    }
}
```
Two consequences: (a) the call occupies a dedicated Media3 loader thread for the whole resolution (up to the 15 s `sourceDeadline`); (b) **`runBlocking` creates a coroutine that is not a child of the loader's job**, and Media3's `Loader.cancelLoading()` only calls `LoadTask.cancel(false)` -> `onLoadCanceled()` and does **not** interrupt the executor thread. When the user seeks away, removes the item, or the player is released, the in-flight resolution keeps running to completion, the `StreamCache` single-flight slot stays occupied, and the loader thread stays parked.
* **Cause.** A suspend-based resolution placed behind a synchronous framework callback with a blocking bridge.
* **Trigger.** Any remote track; worst case a slow provider, or a seek/queue change during resolution.
* **User impact.** A visible stall of up to 15 s at the start of a track whose provider is slow, plus an unabandonable network request. Under repeated seeks several loader threads are parked at once.
* **Reproduction.** Instrument the resolver with a log before/after `runBlocking` and observe the gap; start a track on a slow provider, seek away within a second, and confirm the first resolution still runs to completion.
* **Fix.** Move the resolution out of the synchronous `open()` contract — resolve the item about to play in a service coroutine and substitute the resolved URI, or serve the stream through an out-of-band local proxy (the desktop oracle's design, `core/proxy.py`). At minimum, bridge through a `Future`/`ListenableFuture` the loader's cancellation can cancel, instead of `runBlocking`.
* **Fix side effects.** Resolving ahead of the item means the URL can expire between resolution and playback, and the resolved URL would be visible in the `MediaItem` handed to external controllers unless the URI is kept internal. A cancellable bridge adds a failure mode (cancellation must surface as a playback error, not a hang).
* **Prior art:** `android/review/REVIEW_RESOLUTION.md:40` already declared the blocking part open; this report sharpens it — the wait is also **not cancellable**, which the resolution text did not state.

### P2-10 — Replacing the current `MediaItem` in place is reported as a media-item *transition*, splitting one listen into two sessions and marking the first "completed"

* **Area:** AN-03 (PlaybackService) · **Found by:** B
* **Files:** `android/app/src/main/java/ru/nedotify/app/player/PlaybackService.kt:110-117`, `:274-285`; `android/app/src/main/java/ru/nedotify/app/player/ListeningHistory.kt:14-20`
* **Status:** CONFIRMED (the Media3 reason mapping was read from the 1.11.1 bytecode)
* **Description.** `refreshQueueSources` swaps the current queue entry for the same track with a different `MediaItem` (a different URI: `nedotify://track/<id>` -> `nedotify-offline://track/<id>`, plus an `OfflineAsset` tag) via `player.replaceMediaItem(index, item)`. A different URI means a different `MediaSource`, hence a different window uid, hence Media3 reports it through `onMediaItemTransition` — which the service interprets as "the user moved to another track":
```kotlin
override fun onMediaItemTransition(item:MediaItem?,reason:Int) {
    recovery?.cancel();retryCount=0
    val newQueue=explicitQueueBoundary;explicitQueueBoundary=false
    if(!decks.isHandover)history.transition(item?.mediaId,
        reason==Player.MEDIA_ITEM_TRANSITION_REASON_AUTO || reason==Player.MEDIA_ITEM_TRANSITION_REASON_REPEAT,
        forceNewSession=newQueue || reason!=Player.MEDIA_ITEM_TRANSITION_REASON_PLAYLIST_CHANGED)
}
```
`MEDIA_ITEM_TRANSITION_REASON_PLAYLIST_CHANGED` is the **only** reason for which `forceNewSession` can be false, and in Media3 1.11.1 it is emitted only when the player was **not** playing. While playing, a source replacement always yields `AUTO`/`SEEK` -> `forceNewSession = true` **and** `completedPrevious = true`. That contradicts the contract written in `ListeningHistory` itself: *"Switching the same recording from a signed URL to a local/offline URI is a source refresh, not another listen."* — the branch implementing that contract is unreachable for an in-place replacement.
* **Cause.** The service re-derives the listening-session boundary from Media3's coarse 4-value transition-reason enum, although the service is the component that performed the replacement and already knows the item was replaced in place rather than advanced to.
* **Trigger.** The current item is replaced while playing — i.e. offline mode is toggled on while a *downloaded* track plays, or the current downloaded track is re-downloaded (its generation changes).
* **User impact.** The report shows **two** sessions for one listen, and the first is flagged `completed = true` although the user never finished the track. `completedSessions` and `sessions` are inflated. The total listened ms is preserved (the rows are summed), so no time is fabricated — but the session/completion semantics are wrong, and they diverge from the desktop oracle where one listen is one record.
* **Reproduction.** Download a track, start playing it, then toggle offline mode on. Inspect `history`: two rows for the same `trackId`, the earlier with `completed = 1`.
* **Fix.** Have the service tell `ListeningHistory` explicitly when a replacement is a source refresh (e.g. `history.transition(id, completedPrevious = false, forceNewSession = false)`), instead of inferring it from the transition reason.
* **Fix side effects.** The transition listener would then have to suppress the subsequent automatic `onMediaItemTransition` for the same media id (a one-shot suppression flag). `forceNewSession=false` also means the clock is not reset, so the elapsed time continues accumulating across the source change — the intended behaviour.

### P2-11 — A closed pending-selection gate swallows the user's Play command with no error and no state change

* **Area:** AN-05 (queue) · **Found by:** A
* **Files:** `android/app/src/main/java/ru/nedotify/app/player/DualDeckPlayer.kt:230-231`; `android/app/src/main/java/ru/nedotify/app/player/PlaybackService.kt:85-88`; `android/app/src/main/java/ru/nedotify/app/player/PendingSelectionGate.kt:21-30`
* **Status:** CONFIRMED
* **Description.** `PendingSelectionGate` has three states: idle-open, pending-open, and **closed** (`interruptPending()` cancelled the pending future, `pending == null`, `playAllowed == false`). While closed, `handleSetPlayWhenReady(true)` returns `Futures.immediateVoidFuture()` — no player action, **no `SessionError`**, and the controller is told "success", because `onPlayerCommandRequest` returns `RESULT_SUCCESS` unconditionally and Media3 answers the controller at *enqueue* time (`MediaSessionStub.queueSessionTaskWithPlayerCommand` -> `onPlayerCommandRequestOnHandler` -> `addToCommandQueue`), i.e. **before** the gate is consulted. * **Reproduction.** Issue a pause/noisy while a queue set is being resolved (`readQueue` -> `queueTracks` on `Dispatchers.IO`), then press Play. The first Play is dropped without any message. Unit-level: closed gate + `handleSetPlayWhenReady(true)` -> no player call, no error emitted — no test asserts any user-visible signal for this path.
* **Fix.** Give the refusal a user-visible signal — expose a "play refused" reason on the gate and raise the same `SessionError` the focus-denial path raises.
* **Fix side effects.** An error on every refused play can become noisy; the message must not blame the user and must not be shown when a newer play command is already queued.

### P2-12 — The same interruption cancels the in-flight queue set, silently discarding the user's track selection

* **Area:** AN-05 (queue) · **Found by:** A
* **Files:** `android/app/src/main/java/ru/nedotify/app/player/PendingSelectionGate.kt:21-30`; `android/app/src/main/java/ru/nedotify/app/player/PlaybackService.kt:75`, `:297-319`
* **Status:** CONFIRMED (the Media3 half was read from the 1.11.1 bytecode)
* **Description.** `interruptPending()` does not only close the gate — it calls `future.cancel(false)` on the `onSetMediaItems` future. In Media3 1.11.1 the session installs the resolved items only when that future completes successfully (`MediaSessionStub.handleMediaItemsWithStartPositionWhenReady` -> `Util.postOrRunWithCompletion`, whose runnable is skipped for a cancelled future). A cancelled set therefore means **the resolved queue is never installed**: the previous playlist stays and the user's new selection is thrown away. The app reports nothing — `resolveFuture` only reports *exceptions*; a cancellation takes the `catch(cancelled:CancellationException)` branch and sends no `SessionError`. `MusicViewModel.startPrepared` does not observe the `setMediaItems` future at all, so the failure is invisible on the UI as well.
* **Cause.** The gate conflates two intents. Its documented purpose is to stop *an older queued play* from undoing another controller's pause/noisy; cancelling the *set* future additionally destroys the queue the user just asked for — a side effect the gate does not need, since the `playAllowed == false` check in `handleSetPlayWhenReady` already covers the play.
* **Trigger.** A pause, becoming-noisy, a focus loss, or any command from another controller landing in the window between `onSetMediaItems` and the completion of the queue read (a few ms for a small queue, tens of ms for a 3000-item one).
* **User impact.** The user taps a track; the old queue keeps playing; the new selection never appears; no error, no message. "Tapping a track does nothing."
* **Reproduction.** Make the queue read slow (a 2000+ track library), tap a track, and hit Pause on the notification within the resolution window. Deterministic unit variant: `PendingSelectionGate.begin(future)` -> `interruptPending()` and assert the *set* future is still installable while the *play* is refused.
* **Fix.** Separate "abort the play" from "abort the queue" — `interruptPending()` should close the gate without cancelling the set future (or the service should keep the resolved items and install them paused).
* **Fix side effects.** If the set future is not cancelled, Media3 installs the queue and then runs the controller's queued `prepare`/`play`; the play must still be refused by the gate, which the current `playAllowed` check does — so the "pause must not be undone" invariant is preserved. A user-initiated pause arriving mid-set then leaves the *new* queue installed but paused, which is the intended behaviour.

### P2-13 — A transient audio-focus loss is reported as a "user interaction", cancelling the pending queue selection and the startup queue restore

* **Area:** AN-04 (dual-deck player) · **Found by:** A
* **Files:** `android/app/src/main/java/ru/nedotify/app/player/DualDeckPlayer.kt:248-251`; `android/app/src/main/java/ru/nedotify/app/player/PlaybackService.kt:75`; `android/app/src/main/java/ru/nedotify/app/player/PendingSelectionGate.kt:21-30`
* **Status:** CONFIRMED
* **Description.** `DualDeckPlayer` invokes `onUserInteraction` for `AUDIOFOCUS_LOSS_TRANSIENT` — a *recoverable* event by definition. The service implements `onUserInteraction` as "the user changed the playback intent" and it (a) bumps `interactionVersion`, (b) cancels the queue-restore job, (c) cancels the pending `setMediaItems` future and sets `playAllowed=false`, (d) cancels the error-recovery job.
* **Cause.** The callback conflates "the user's intent changed" with "the system took the audio focus away". `PlaybackFocusState` already models the difference (`transientLoss()` keeps `requested=true`; `stop()` clears it), but the callback invocation does not follow it.
* **Trigger.** The user taps a track while a `setMediaItems` is in flight and another app takes transient focus (a navigation prompt, a voice assistant). The same happens at app start while the saved queue is being restored.
* **User impact.** The tap silently does nothing — no queue, no playback, no error — and the user must tap again. At startup the saved queue is dropped and the app opens with an empty queue.
* **Reproduction.** Instrument `onUserInteraction`, or set a breakpoint on `PendingSelectionGate.interruptPending`; drive `DualDeckPlayer.audioFocusChanged(AUDIOFOCUS_LOSS_TRANSIENT)` while `PendingSelectionGate.pending` is non-null. No such test exists today.
* **Fix.** Split the callback into "user intent changed" and "playback interrupted by the system". The transient branch should not invoke the user-interaction callback — the play intent is already preserved in `focusState`, and `cancelTransition()` + `active.pause()` cover the player side.
* **Fix side effects.** The gate exists to drop a stale "prepare/play" queued before a competing pause/noisy, so the fix must keep the "stale play must not undo another controller's pause/noisy" invariant while allowing the *set* itself to survive.

### P2-14 — A cross-device restore permanently duplicates local tracks and points playlists at the unplayable copy

* **Area:** AN-07 (backup) · **Found by:** B
* **Files:** `android/app/src/main/java/ru/nedotify/app/data/BackupMerge.kt:6-22`; `android/app/src/main/java/ru/nedotify/app/data/BackupCodec.kt:44-58`; `android/app/src/main/java/ru/nedotify/app/data/LibraryRepository.kt:72-74`
* **Status:** CONFIRMED
* **Description.** An incoming local track is matched to an existing library row **only** by the portable id, which is salted with the *source* device's library id (`portableTrackId(track, libraryId)` = SHA-256 of `libraryId + '\0' + track.id`). On restore, existing rows are hashed with the *destination* device's library id, so a backup produced by another device can never match. The local track is inserted as a new `portable-local:<hash>` row with an empty `localUri`, while the destination's own copy (`local:<mediaStoreId>`) stays. The song appears twice and the restored playlist links point at the placeholder — unplayable until the user re-attaches a file. The app has **no** track-deletion affordance anywhere (`dao` exposes only `deletePlaylist`, `deleteSmartPlaylist`, `deleteDownload`, `removeFromPlaylist`), so the duplicate cannot be removed.
* **Cause.** The identity model conflates "same physical file" with "same library + same native id", and the library id is by design never replaced by an import.
* **Trigger.** Device B already has file F in MediaStore; the user restores a JSON backup exported from device A that contains F.
* **User impact.** The library permanently gains a duplicate, unplayable entry; every restored playlist contains the dead copy. The only recovery is clearing app data.
* **Reproduction.** Pure-JVM on the existing `BackupMerge` seam: `plan(BackupSnapshot(tracks=[Track("local:123", …, source="local")]), backup(tracks=[Track(portableIdFromOtherLibrary, …, source="local")]), libraryId)` -> the plan contains **two** tracks for the same file and `plan.links` reference the portable id. `BackupMergeTest` has no case for a cross-device local import; the closest test (`anotherDevicesMediaStoreIdCannotOverwriteThisDevicesFile`) asserts only that the native id is *not* overwritten — never that the file is not *duplicated*.
* **Fix.** When an incoming local track has no portable-id match, try to reconcile it with an existing local row by content (title+artist+duration) and reuse that row's id; or at minimum surface the collision in the import notice and provide a way to drop the placeholder.
* **Fix side effects.** Content matching can merge two genuinely different files with identical tags; warning + allowing removal is safer than auto-merging. A track-deletion affordance is a wider product change.

### P2-15 — Exporting a library with more than 20 000 tracks fails outright, and the error uses the read-side wording

* **Area:** AN-07 (backup) · **Found by:** B

* **Description.** `encode` starts with `checkCounts`, which rejects more than 20 000 tracks (and >2 000 playlists, >100 000 links, >100 000 sessions) with `invalid("слишком много записей")`. `invalid` hard-codes the prefix `"Не удалось прочитать копию: "` for **both** directions, so pressing "Сохранить копию" on a large library shows *"Не удалось прочитать копию: слишком много записей"* — a read error on a write path. ### P2-16 — Decoding a backup the codec itself accepts needs ~120–150 MB of heap; the OOM escapes every `catch (Exception)` and kills the process

* **Area:** AN-07 (backup) · **Found by:** B
* **Files:** `android/app/src/main/java/ru/nedotify/app/data/BackupCodec.kt:116-124`, `:111-113`; `android/app/src/main/java/ru/nedotify/app/data/LibraryBackupStorage.kt:27-42`; `android/app/src/main/java/ru/nedotify/app/ui/MusicViewModel.kt:266`
* **Status:** CONFIRMED (heap profile measured on the JVM with the project's own `org.json:json:20250517`; the device heap limit was not measured)
* **Description.** The format is bounded at 16 MB, but the *decoded* representation is not. The import path holds (a) the raw file bytes, (b) a **second** full copy from `ByteArrayOutputStream.toByteArray()`, (c) the decoded UTF-16 `String`, (d) the `JsonShape` grammar pass's transient `StringBuilder`s, and (e) a full `org.json` DOM. Measured with the same org.json version the project uses: a **16.4 MB** document (20 000 tracks + 70 000 sessions + 80 000 links — all inside the codec's own `MAX_TRACKS`/`MAX_SESSIONS`/`MAX_LINKS`) costs **87 MB** for the DOM alone, **120 MB** live after DOM + `toString()` + `toByteArray()`, and the JVM **threw `OutOfMemoryError` at `-Xmx160m`** (survived at 256 MB). The Android platform `org.json` is a different implementation with the same `LinkedHashMap`/`ArrayList` DOM shape, so the order of magnitude carries over. `OutOfMemoryError` is an `Error`: `BackupCodec.decode` (`catch (_: Exception)`) and `MusicViewModel.backupTask` (`catch(error:Exception)`) do not catch it, so the process dies.
* **Cause.** The codec materialises the whole document three to four times over instead of streaming, and the read path duplicates the input array before parsing.
* **Trigger.** A large backup near the 16 MB cap on a device with a ~128–192 MB app heap limit.
* **User impact.** The app crashes while importing/exporting a large backup instead of reporting an error; the library is not damaged (the Room transaction rolls back) but the user sees the app die.
* **Evidence.** `LibraryBackupStorage.kt:29-41` (BAOS buffer + `toByteArray()` + decode); `BackupCodec.kt:119-124` (String + strict-JSON pass + full DOM); `MusicViewModel.kt:266`. Measured: `json utf8 bytes = 16 405 803` (cap 16 777 216) -> `heap after DOM = 87 MB`, `after String = 104 MB`, `after bytes = 120 MB`; `OutOfMemoryError` at `-Xmx160m`; re-parse took 619 ms at `-Xmx256m`.
* **Reproduction.** Run the scratch measurement with the project's org.json jar at `-Xmx160m` and a 16 MB document, or import a max-size backup on a low-RAM device and watch for an OOM kill.
* **Fix.** Drop the `toByteArray()` copy (read into a right-sized array), parse incrementally, or lower `MAX_BYTES` to what the device can hold — and convert `OutOfMemoryError` into a `SourceFailure` so the user gets a message instead of a crash.
* **Fix side effects.** Lowering `MAX_BYTES` makes large libraries un-backupable (interacts with P2-15); a streaming parser is a large rewrite of `BackupCodec`.

### P1-05 - Local library search is a full table scan with no index and no FTS; it silently exceeds the aggregate's 6.5 s per-source budget and drops local results from the "Все" search

* **Area:** AN-12 B - **Files:** `data/LibraryRepository.kt:55-67`; `data/Models.kt:104-105`; `data/SearchAggregate.kt:16,22`; `ui/SearchScreen.kt:90-93`
* **Status:** CONFIRMED (the query plan, the absence of the index, and the timings were all reproduced against the exact exported schema and SQL)
* **Description.** The "На устройстве" (local) source is implemented as *paging over the whole `tracks` table in Kotlin*, not as a database query. `dao.searchPage(500, offset)` selects `id,title,artist` from **all** rows where `localUri!='' OR id IN (completed downloads)`, ordered by `addedAt DESC`, with `LIMIT 500 OFFSET n`. The Room entity declares only two indices - `index_tracks_source` and `index_tracks_favorite` (`schemas/.../3.json:98-113`) - so `ORDER BY addedAt DESC` has **no supporting index**. `EXPLAIN QUERY PLAN` on the reproduced schema:
  ```
  SCAN tracks
  LIST SUBQUERY 1
  SCAN offline_downloads
  CREATE BLOOM FILTER
  USE TEMP B-TREE FOR ORDER BY
  ```
  Every page re-scans the whole table and re-sorts it. The Kotlin loop keeps paging until 100 matches accumulate **or the table is exhausted** - so a query that matches nothing walks the entire library, and the total work is O(N^2/500) row visits. The desktop does the opposite: `core/database.py:395` creates a real FTS5 index (`tracks_fts` over title/artist/album/genre) with insert/update/delete triggers, and `search_tracks` queries it with per-word prefix matching before falling back to `LIKE`.

  | library size | Android paged scan | desktop FTS5 |
  |---|---|---|
  | 1 000 | 5.5 ms / 1 000 rows read | 0.50 ms |
  | 10 000 | 117 ms / 10 000 rows read | 1.16 ms |
  | 50 000 | **13 943 ms** / 50 000 rows read | - |
  | 100 000 | **63 456 ms** / 100 000 rows read | 10.54 ms |

* **User-visible effect.** The "Все" tab calls `aggregateSearch(listOf({search(query,"local")}, {soundCloud.search(query)}, {youtube.search(query)}))` (`LibraryRepository.kt:69`), and `aggregateSearch` wraps each task in `withTimeout(providerTimeoutMs)` with the default `6_500` ms. The local task therefore gets **the same 6.5 s budget as a network provider**. The measured crossover is ≈ 35 000-40 000 tracks; at 40 000 the no-match scan already takes 11.7 s. On such a library the scan is cancelled mid-flight -> `TimeoutCancellationException` -> `Result.failure` -> the local tracks are dropped from the merged list. The missing piece is the index/FTS the desktop has; the missing piece #2 is that the local source is not given its own (larger) budget separate from the network sources, even though it is a local, non-network operation.
* **Trigger.** A device library of tens of thousands of tracks (reachable with lossless/FLAC collections), then any "Все" or "На устройстве" search whose result set is smaller than 100 rows.

* **Evidence.** `data/LibraryRepository.kt:55-67` (the paging loop), `data/Models.kt:104-105` (the query), `schemas/.../3.json:98-113` (the only two indices), desktop `core/database.py:395-400,786-808` (FTS5 DDL + `MATCH` query).

* **Fix.** Push the filter into SQL and add an index that supports the query - or, closer to the oracle, add an FTS table with the same triggers the desktop uses and query it with per-word prefix terms. Separately, give the local source its own budget (it is not a network call) so a slow local scan can never be silently discarded.

* **Status:** CONFIRMED
* **Description.** `CatalogMatcher.resolve` takes a list of *network searchers* and runs them one after another, each a full provider search. The caller `importCatalog` then loops over up to **500** catalogue tracks **one at a time**. So a 500-track import performs up to 500 x 2 = **1 000 sequential third-party searches**, each with its own 20 s timeout, on the `viewModelScope` critical path. At a realistic 1-2 s per round trip that is 17-33 minutes of wall clock for one import.
  The desktop does the same job with a bounded-concurrency batch: `TrackResolver.resolve_tracks` submits to a pool of 8 (`MAX_CONCURRENCY = 8`), bounds the *whole batch* to 10 s (`BATCH_TIMEOUT`), memoises results for 300 s with a 512-entry cap, and tries the **local database first** before hitting the network at all. The Android matcher has no local-first step, so a catalogue track already in the user's library still costs two network round trips.
* **Note (in the Android's favour).** The Android matcher is materially *stricter* than the desktop's on quality: title similarity >= 0.86, author >= 0.70, matching version tags, duration within 8 s / 4 % (the desktop accepts 0.6 with no version or duration check). The finding is purely about the *cost* of arriving at that verdict, not about the verdict.
* **Relation to P2-08.** P2-08 recorded the import as "an unbounded, non-resumable batch"; this is the same defect with the exact multiplication (500 x 2) and the desktop's batch-resolver shape as the reference.

### P3-115 - `LibraryRepository.search` has three mutually exclusive exit paths with different providers, different timeouts and different result shapes; the "all" path is not a superset of the per-source paths

* **Area:** AN-12 B - **Files:** `data/LibraryRepository.kt:54-71`; `data/SearchAggregate.kt:16-32`
* **Description.** (1) The `"all"` branch re-enters `search(query,"local")`, re-running the whole paging scan as a nested `withContext(Dispatchers.IO)` inside an `async` inside a `supervisorScope` - an extra coroutine hop and an extra scan of the same table. (2) The per-source branches return **no** timeout at all: `youtube.search(query)` / `soundCloud.search(query)` are bounded only by the `MusicNetwork` client's own 12/20/30 s timeouts. Only the `"all"` branch gets `providerTimeoutMs` - so the same query under "YouTube Music" waits up to ~30 s with a spinner while under "Все" it is capped at 6.5 s. The desktop applies its 6 s deadline uniformly. (3) The `"local"` branch returns full `Track` rows carrying `localUri`/`mimeType`; the network branches return `Track`s without them, and `SearchScreen` renders both through the same `TrackRow` - the same row type means "playable from a provider" and "playable from a file". (4) The offline check sits *after* the `"local"` branch but *before* the `"all"` branch, so the behaviour is a property of statement order rather than of an explicit policy.
* **Fix.** Fold the three branches into one table of sources (name, timeout, search block) and give the local source its own budget and dispatcher, so the "all" path is literally the composition of the same entries the single-source paths use. Preserve the offline behaviour explicitly rather than by statement order.
* **Architecture note.** The "source" concept exists only as a string literal (`"local"`, `"soundcloud"`, `"youtube"`) compared with `==` at six sites, and the provider pair is spelled out in **two** places with different shapes (`LibraryRepository.kt:69-70` and `MusicViewModel.kt:354`) - a new provider must be added to both and the two lists can drift. The natural seam is a small `SearchSource` interface, which would simultaneously give per-source attribution and per-source budgets.

### P3-116 - The local scan's `OFFSET` pagination is not snapshot-stable: a track added or removed during the scan is returned twice or not at all

* **Area:** AN-12 B - **Files:** `data/LibraryRepository.kt:57-66`; `data/Models.kt:104-105`
* **Status:** CONFIRMED (reproduced against the exact schema and SQL)
* **Description.** The local scan reads the table in 500-row pages using `LIMIT ... OFFSET ...` over an **unstable** ordering. `ORDER BY addedAt DESC` is not a total order (millisecond resolution, many rows share a value), and a newly-inserted row lands at the *front*. Between page 1 and page 2 the window therefore shifts: a row inserted at the front is read **twice**, and a row deleted in that window is read **not at all**. The reproduction (exact DDL, exact SQL, 1 200 rows, one insert between the two page reads) returned a shared id in both pages. The Kotlin loop appends ids without de-duplication, and the final projection is `matches.take(100).mapNotNull {found[it]}` - so the same id can appear **twice** in the returned list. The aggregate's `distinctBy { it.id }` removes the duplicate for the "Все" path, but the **direct "На устройстве" path** has no such de-duplication.
* **Trigger.** The library changes *while* a local search is running - i.e. exactly when the scan is slow (P1-05), which is when the user is most likely to start playback (`dao.remember` inserts on every play) or let a download land.
* **Impact.** A track appears twice in the "На устройстве" list, or a matching track is missing from it, with no error. The visible effect is a repeated row and an inflated "Найдено треков: N" counter.
* **Fix.** Largely subsumed by P1-05 - pushing the filter into a single SQL query removes the paging entirely and with it the drift. If the paged scan is kept, page by a stable, unique key (`id > lastId ORDER BY id`) instead of by `OFFSET`, and de-duplicate the accumulated ids.
* **Fix side effects.** Ordering by `id` changes the result order (from most-recently-added to lexicographic), which is user-visible; the desktop orders local results by `play_count DESC` anyway, so a deliberate ordering decision is needed either way.

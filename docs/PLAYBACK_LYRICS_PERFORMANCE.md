# Ускорение воспроизведения и текстов

15 октября 2026 года. Изменения применяются после перезапуска приложения.

## Запуск треков

При выборе трека из большой очереди больше не выполняется поиск LUFS для каждого её элемента. Обогащение громкости выполняется для выбранного трека и при последующей активации других треков. Регрессия с 10 000 элементами проверяет, что обрабатывается только выбранный элемент; нормализация, очередь и учёт прослушивания сохранены.

Предварительная подготовка следующего трека теперь проходит через `AudioEngine.resolve_stream_url` и общий `StreamResolver`, поэтому результат доступен обычному запуску через кеш. Для подготовки выделены два работника, независимо от поиска, с ограничением двух ожидающих/выполняющихся заданий и объединением одинаковых запросов. Копия трека защищает очередь от фоновых изменений. Обслуживание дискового кеша выполняется после разрешения URL.

Закрыты гонки между промахом кеша и регистрацией общего запроса в StreamResolver/YouTube: завершившаяся подготовка не должна вызывать повторное извлечение потока. SoundCloud запоминает успешную проверку CDN уже при первом разрешении; одновременные обращения к ещё не проверенному URL выполняют одну проверку в работнике. Ранее первый повтор мог снова ждать сетевую проверку с таймаутом до трёх секунд.

Явно истёкшие `expire`/`Expires` отбрасываются локально, без пробного обращения к CDN, включая быстрые ветки API. TTL и LRU не продлеваются от чтения. Семантика `Expires`: [официальная документация CloudFront](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-creating-signed-url-canned-policy.html).

В интерфейсе повторная загрузка того же URL использует уже подготовленный Audio/HLS вместо сброса буфера. Разные формы proxy URL не считаются одинаковыми только по похожему названию трека: в таком случае ускоряется разрешение через общий кеш, но перенос готового буфера между URL не гарантируется.

## Тексты

- RAM-кеш сервиса увеличен с 500 до 2048 результатов. Дополнительный кеш интерфейса хранит 40 завершённых успешных результатов.
- Рядом с основной SQLite-базой создаётся отдельный `lyrics_cache.db`: до 20 000 проверенных результатов, лимит полезных данных 96 MiB, ограничение основной SQLite-файла 128 MiB. Журнал WAL имеет собственное ограничение. Это постепенно наполняемый кеш, готовый корпус песен не скачивается.
- Проверенные синхронизированные тексты сохраняются на 30 дней, обычные — на сутки. Ошибки сети и недоступность источников не записываются на диск как отсутствие текста. Повреждение/занятость кеша означает промах, а не отказ плеера.
- Поиск использует существующие пять источников; общий пул увеличен до шести работников. Netease/QQ рассматривают до 12 кандидатов, сначала по подходящей длительности, продолжают после пустого текста первой версии. LRCLIB рассматривает всю полученную страницу.
- Первый подходящий обычный текст публикуется сразу; при известной длительности поиск синхронизированной версии продолжается в пределах общего бюджета восемь секунд. При неизвестной длительности достоверный обычный текст завершает поиск без лишнего ожидания.
- Открытие панели текста во время поиска не запускает ту же работу заново. Временные CDN-ссылки исключены из идентичности текста; локальные файлы учитываются вместе с временем изменения. Исполнитель, редакция, альбом и длительность продолжают участвовать в проверке.
- Устаревшие ответы, неверные ревизии и текст другой версии не подменяют текущий результат. Промежуточные ответы и ошибки не попадают в кеш интерфейса. Длительность из Audio может один раз уточнить запрос; зависший запрос допускает повтор.

Новые зависимости и внешние API не добавлены. Большая база сама по себе не создаёт отсутствующих текстов: первый поиск по незнакомому треку зависит от источников и сети.

## Проверки и измерения

Полная локальная suite:

```powershell
& ".venv_win\Scripts\python.exe" -m pytest -q
```

**1257 passed, 1 skipped, 3 xfailed**, 54,23 секунды. Пройдены тесты моста, очереди, учёта прослушивания, резолвера, кешей, DRM, отказов провайдеров, текстов и выполнения настоящих JS-функций с подменёнными Audio/HLS и мостом. Внешние network-тесты не включались. `git diff --check` не обнаружил ошибок пробелов.

Новые регрессии: `test_playback_startup_performance.py`, `test_stream_startup_performance.py`, `test_lyrics_performance.py`, `test_playback_latency_ui.py`.

Воспроизводимый замер кеша текстов:

```powershell
& ".venv_win\Scripts\python.exe" tests/benchmark_lyrics_cache.py
```

Семь песен, источник подменён с задержкой 150 мс. Медианы последнего запуска: первый результат 158,321 мс; полный холодный запрос с записью 191,363 мс; повтор RAM 0,253 мс; чтение после создания нового сервиса 6,553 мс. Вызовов источника — семь, только для холодных запросов. Это измерение локального кеша на стенде, а не обещание скорости реальных серверов.

Отдельный изолированный замер: 10 000 обращений к прогретому StreamResolver — 102,39 мс без сетевых каскадов; 10 000 повторов SoundCloud — 73,36 мс, без дополнительных API/CDN-проверок после первого разрешения. Сетевые обращения были подменены.

Реальное приложение в этой работе не запускалось и не перезапускалось, EXE не собирался. Тесты используют временные базы; пользовательская библиотека не очищалась. Измерение первого звука на настоящих провайдерах ещё не выполнялось.
